## 0. 已确认的决策

这一轮澄清把下面四点定下来了，后文按它们展开：

1. **同一个 `BumpListAlloc` 的所有 Page 大小完全相同，且页大小来自有限选项**，不是用户
   传入的任意 `usize`。页大小是 2 的幂（1 KiB、2 KiB、4 KiB……），并受
   `BlockHeader` 的 `u16` 位置下标约束：
   `page_size <= (1 << 15) * size_of::<usize>()`。64 位平台上限 256 KiB，32 位平台上限
   128 KiB。单次分配必须落在一页内；超过页容量直接返回 `AllocError`，不做跨页或
   临时大页。不规则页链表留作后续独立项目。
2. **两把锁、两层职责**：
   - `BumpListAlloc` 自己有一把锁，只负责 Page 链表的维护（`head_` / `tail_`、
     `prev_` / `next_`、挂链/摘链）；
   - 每个 Page 有自己的锁，负责本页的 bump 游标、活跃块计数与块链；
   - `BlockHeader` 通过 `u16` 位置下标快速反推 Page 首地址，因此归还内存的快路径
     只需要 Page 锁，不需要 `BumpListAlloc` 的链表锁。
   这沿用 StrongPool 的“页锁 + 链锁”分层意图；sw-scope 的 `StrongPool::of_chunk_`
   文档也已经写明“线程安全的池在归还块时需要先反查池地址并取得池锁”
   （[pool_.rs](../../sw-scope/src/strong_/pool_.rs#L104-L121)）。
3. **页内块链**：`BlockHeader` 的 8/4 字节里，除 `u16` 位置下标外再用一个 `u16` 保存
   块链后继（下一个块头的 cell 下标）；`order_flags` 的最高位标记已释放。分配时回填
   前一块头的后继，释放时不破坏链，因此可以从 Page 的 `first_` 扫描整页的存活/已释放
   块，用于 debug 与 `BumpListAlloc` 析构时的未释放内存警告。页内释放的块仍然**不会
   被重新分配**。
4. **空页只保留一个**：`PageState` 不再有 `retiring`。一个 Page 的 `live_` 归零时，
   把它重置为初始 bump 状态：如果它已经是 `tail_`，直接保留；如果它还不是 `tail_`
   且当前没有空 tail，就把它挪到 tail 保留复用；如果已经有一个空 tail，则把多出来的
   这个空页摘链归还。这样 `BumpListAlloc` 始终最多缓存一个空 Page，且这个空页总是
   `tail_`。`Page` 头也不再保存 `base_` 自指指针：页内地址从 `NonNull<Page>` 的原始
   指针偏移得到；所有 Page 相关 struct 使用 `#[repr(C)]` 并手动按大小编排字段，减少
   padding。

## 1. 目标与非目标

### 1.1 目标

`bumplist-alloc` 是一个以固定大小 Page 为基本单元、页内 bump 分配、页间用指针串成
链表的 arena，并且是标准的 `core::alloc::Allocator`（该 trait 自 Rust 1.100 起稳定）。

- **只对 `&BumpListAlloc` 实现 `Allocator`**：分配块的生命周期由 `&BumpListAlloc`
  的借期携带，不需要 `Retain<T>`、弱槽位或引用计数。
- **默认 `Send + Sync`**：底层分配器为 `Global` 时，`BumpListAlloc<Global>` 可直接跨线程
  共享；`&BumpListAlloc` 也因此是 `Send + Sync`。
- **不实现 `Clone`**：需要共享时使用共享引用（`&` / `Arc`），而不是复制 allocator。
- **固定页大小**：每个实例创建时从有限 `PageSize` 选项中选择一个；该实例的所有 Page
  都是这个大小。同一实例不会出现大页/小页混用。
- **Page 头在页内**：`prev_` / `next_`、owner 指针（最低位兼作页锁）、页状态与空页
  回收回调都在 Page 起始处，因此每页可交给
  用户的内存小于页大小。
- **块对齐**：每个用户块至少按指针宽度对齐（64 位为 8 字节），并满足
  `Layout::align()`。
- **块级页回查**：每个块通过 `BlockHeader` 的 `u16` 位置下标 O(1) 反推所属 Page。
- **页内块链**：`BlockHeader` 的第二个 `u16` 保存块链后继；可从 `PageState.first_`
  扫描整页的存活/已释放块，供 debug 与析构时检查未释放内存。
- **空页复用与归还**：一页上的全部块都被释放后，重置为初始 bump 状态；把它挪到
  `tail_` 保留复用。若已经有一个空 tail，则把多出来的空页归还给底层分配器。因此最多
  缓存一个空 Page。
- **`no_std` 可用**：只依赖 `core` 与 `alloc`，不依赖 `std`；锁使用自旋锁。可选的
  `std` 特性用于析构时把未释放块警告写到 stderr。

### 1.2 非目标（v1 不做）

- **不做跨页大块**：一个用户块必须完整落在一个 Page 内。请求超过页可容纳空间时返回
  `AllocError`，不存在“申请一个更大的 Page”的路径；需要不规则页链表时另做一个项目。
- **不做单块空闲链复用**：释放块只减少页的 `live_` 并标记块头 `FREE_BIT`，不把块挂回
  空闲链；页内空洞保留到整页空掉。整页空掉后，tail 空页重置复用，其它空页归还。
- 不实现 `Retain` / 弱引用 / 强引用计数 / 类型擦除析构；这些属于 sw-scope 的上层机制。
- 不做 `reset`、`shrink_to_fit` 等额外 API；需要时再讨论。
- 不实现 `Clone`。
- 不做 per-thread cache、对象回收或段合并。

## 2. 从 sw-scope 继承什么、剥离什么

### 2.1 StrongPool 的关键设计

`StrongPool` 是“池头 + 定长 cell 数组”的内嵌式 bump 池：

- 池头（`prev_pool_`、`cell_count_`、`used_count_`）位于整块内存起始处；
- cell 步长固定为 8 字节，分配时按 `Layout::align()` 向上对齐并推进 `used_count_`；
- 每个 StrongChunk 头部保存 `pool_order_`（起始 cell 序号），归还/析构时用
  `块地址 - 池头大小 - pool_order * CELL_SIZE` 反推池地址；
- 池之间用 `prev_pool_` 串成链；
- StrongPool 只 bump、不单独回收 chunk；Scope 静默时整条强池链一次性释放。

对应代码：

- 池头与布局：[`StrongPool`](../../sw-scope/src/strong_/pool_.rs#L36-L58)
- 反推池地址：[`of_chunk_`](../../sw-scope/src/strong_/pool_.rs#L104-L121)
- 对齐 bump 分配：[`allocate_with_order_`](../../sw-scope/src/strong_/pool_.rs#L168-L200)
- 块头保存 `pool_order_`：[`StrongChunkBase`](../../sw-scope/src/strong_/chunk_.rs#L80-L101)

### 2.2 WeakPool 的关键设计

`WeakPool` 与 StrongPool 共享“池头在块首、数组紧随其后”的布局，但多了：

- 槽位空闲链（`latest_free_`，链接借用槽位自身内存）；
- 原子活槽计数 `live_count_`；
- 空池摘链协议（`pins_` / `retire_pending_` / `detached_`），最后一个槽位归还后把空池
  从域链上摘下并释放。

参见 [`WeakPool`](../../sw-scope/src/weak_/pool_.rs#L342-L470)。

### 2.3 bumplist-alloc 的取舍

```text
StrongPool 的“Page 头 + Page 链 + 页内 bump + 块头反查”骨架
        +
WeakPool 的“live 计数 + 空页摘链归还”思想
        +
每 Page 一把锁，归还快路径不碰 BumpListAlloc 链表锁
        -
弱槽位 / Retain / 强计数 / 类型擦除 / Scope 生命周期
```

因此它保留：

- Page 头在页内、页间双向指针；
- 页内 bump，不复用已释放块的中间空洞；
- 每页一个活跃块计数，用来判断整页是否已空；
- 块头记录自身在页内的位置，用于 O(1) 反查 Page。

它不保留：

- `WeakSlot` 的身份槽位与状态机；
- `StrongChunk` 的强计数、`Predrop`、vtable 析构；
- `ScopeInner` 的域锁、句柄计数与 flush 流程。

## 3. 常量、PageSize 与容量上限

### 3.1 指针宽度与 cell

```text
P = size_of::<usize>()          // 64 位为 8，32 位为 4
```

Page 内以 `P` 字节为一个 cell。`BlockHeader` 占一个 cell，用户块从下一个 cell 开始。
用户块至少按 `P` 对齐；`Layout::align()` 大于 `P` 时在页内继续向上对齐。

### 3.2 位置下标与页大小上限

`BlockHeader` 只用一个 `u16` 记录“自身所在的 Page 内 cell 下标”（记作 `order`）：

```text
order = (header_addr - page_base) / P
page_base = header_addr - order * P
```

按约定 `order` 只使用 15 位，因此：

```text
MAX_PAGE_CELLS = 1 << 15 = 32768
MAX_PAGE_BYTES = MAX_PAGE_CELLS * P
```

- 64 位：`MAX_PAGE_BYTES = 262144`（256 KiB）；
- 32 位：`MAX_PAGE_BYTES = 131072`（128 KiB）。

所有 `PageSize` 选项都必须满足 `page_size / P <= MAX_PAGE_CELLS`。

### 3.3 `PageSize` 有限枚举

页大小不由用户输入 `usize`，而是有限枚举。当前实现的集合是 2 的幂：

```rust
pub enum PageSize {
    P1K, P2K, P4K, P8K, P16K, P32K, P64K, P128K, P256K,
}
```

- `PageSize::P256K` 在 64 位可用（32768 cells），在 32 位会得到
  65536 cells，超过 `MAX_PAGE_CELLS` 与 `u16` 的可用范围，因此 32 位构造返回
  `BumpListAllocError::UnsupportedPageSize`。
- 当前枚举名为 `P1K` / `P2K` / …；如果以后决定只保留 1 KiB–128 KiB，可以让所有平台
  都支持全部选项，并把 `new` 改为不返回 `Result`。当前实现保留全量选项和
  `Result`。

### 3.4 固定页大小的直接后果

- 一个用户块的可用空间上限约为：
  `page_size - PAGE_HEADER_CELLS * P - P - 对齐填充`。
- 1 KiB 页在 64 位下最多容纳约 1 KiB 减去页头、块头与对齐填充的块；更大的请求返回
  `AllocError`。
- `Vec` / `String` 等容器在增长到超过页容量时会收到 `AllocError`；标准库容器通常会走
  `handle_alloc_error`。使用时应选择足够大的 `PageSize`，或只用于小块场景。
- 不存在跨页拼接或临时大页。

## 4. 内存布局

### 4.1 整体结构

```text
BumpListAlloc<A>
├── alloc_: A
├── page_size_: PageSize
├── page_cells_: u16              // page_size / P
├── page_bytes_: usize            // page_size 的字节数
├── list_lock_: SpinLock          // 只保护 Page 链表
└── inner_: UnsafeCell<Inner>
    ├── head_ ──┐
    ├── tail_ ──┼──> Page A <──> Page B <──> Page C (tail_)
    └── tail_empty_: bool
                │      │            │
                │      └─ Page header（links、used/live/first/last、owner/lock-bit、cleanup）
                │         user area: [BlockHeader][user block]...
                └── ...
```

`head_` 是链头，`tail_` 是链尾，也是分配时优先尝试的页。页间是双向链表，链接字段就在
Page 头里。

### 4.2 Page 头

实际字段：

```rust
#[repr(C)]
struct Page {
    // 由 list_lock_ 保护；2 个指针
    links_: UnsafeCell<PageLinks>,  // prev_ / next_

    // 由本页的页锁保护；4 个 u16
    state_: UnsafeCell<PageState>,

    // 创建本页的 BumpListCore 指针；最低位兼作页锁
    owner_: AtomicPtr<BumpListCore>,
}

#[repr(C)]
struct PageLinks {
    prev_: Option<NonNull<Page>>,
    next_: Option<NonNull<Page>>,
}

#[repr(C)]
struct PageState {
    used_: u16,  // 下一个可 bump 的 cell 下标，初始为 PAGE_HEADER_CELLS
    live_: u16,  // 本页活跃块数
    first_: u16, // 第一个块头的 cell 下标；没有块时为 SENTINEL
    last_: u16,  // 最后一个块头的 cell 下标；没有块时为 SENTINEL
}
```

字段按大小降序手动编排：`PageLinks`（2 指针）+ `PageState`（8 字节）+ `owner_`
（指向 BumpListCore 的指针）。在 64 位平台上 `Page` 为 32 字节，32 位平台上为 20 字节；
`PAGE_HEADER_CELLS = ceil(size_of::<Page>() / P)`，64 位为 4，32 位为 5。
具体值由编译期计算，不写死。

**owner 指针最低位兼作页锁**：`BumpListCore` 至少按指针宽度对齐，owner 指针最低位
必为 0；`lock_` / `try_lock_` 用 `AtomicPtr` 的 CAS 与 `map_addr` 把最低位置 1，
`PageGuard` 析构时清掉。`map_addr` 保留指针 provenance，不把指针存成整数再转回来（满足
strict-provenance）。这样 Page 不需要额外的 `SpinLock` 字段。`Page::release_page_page_` 在页变空时先释放页锁，再直接调用
`BumpListCore::cleanup_empty_page_`（取页锁 + 链表锁，决定保留 / 挪到 tail / 摘链归还）。

`BumpListAlloc<A>` 内联一个非泛型 `BumpListCore`，以及 `alloc_: A`；Page 的 owner 指向
Core。真正需要 `A` 的建页 / 还页由 Core 里两个单态化函数指针完成：Core 保存一个
指向整个 `BumpListAlloc<A>` 的原子指针，函数用
`offset_of!(BumpListAlloc<A>, alloc_)` 从它取出 `A`。因此不需要 `Box<A>`，也不需要每个
Page 保存函数指针；自指针在每次分配 / 归还 / 析构前刷新。

代价是：创建第一个 Page 之后，`BumpListAlloc` 不能被移动（Page 的 owner 指向内联
Core）；需要移动时先 `Box::new(bump)` 固定地址再分配。

**不再保存 `base_`**。Page 首地址就是 `NonNull<Page>` 的原始指针；`try_alloc` /
`release` / `scan_chain` 都额外接收这个 `NonNull<Page>`，用户块与 BlockHeader 从
`page.cast::<u8>()` 偏移写入，provenance 覆盖整页。这样既不浪费一个指针，也不会用
`&Page`（只覆盖 Page 头）的 provenance 去写 Page 头之外的内存。

`used_` / `live_` / `first_` / `last_` 使用 `u16`：页内 cell 数不超过 32768，活跃块数
与块头下标均能容纳。`PageState` 没有 `retiring`；`live_` 归零时由归还路径直接把
`used_` / `first_` / `last_` 重置，Page 回到初始 bump 状态。

### 4.3 BlockHeader 与用户块

```text
Page base
├── Page header（PAGE_HEADER_CELLS 个 cell）
├── ... padding / 对齐填充 ...
├── BlockHeader cell:
│      order_flags: u16   // 低 15 位：自身 cell 下标；最高位：FREE_BIT
│      next_free: u16     // 块链后继 cell 下标；SENTINEL 表示没有后继
│      reserved: P - 4    // 目前不使用
├── user block（layout.size()，向上取整到 cell）
├── padding
├── BlockHeader cell
├── user block
└── ... 直到 page_cells_
```

- `BlockHeader` 占一个 cell（64 位 8 字节，32 位 4 字节），使用开头的两个 `u16`。
- `BlockHeader` 紧挨在用户块之前；用户块从下一个 cell 开始。
- `order_flags` 的低 15 位是 **BlockHeader 自己** 的 cell 下标，不是用户块的；
  最高位 `FREE_BIT` 表示块已释放。
- `next_free` 是页内块链的后继：分配新块时，前一个块头的 `next_free` 会被回填为新
  块头的 cell 下标；新块自己的 `next_free` 初始为 `SENTINEL`。释放块只置
  `FREE_BIT`，不改变链。
- 由用户指针反查：

```text
header    = user_ptr - P
flags     = *(header as *const u16)
cell      = flags & ORDER_MASK
page_base = header - cell * P
```

- `BlockHeader` 不属于用户块 `user_ptr..user_ptr + layout.size()`，而是 allocator 预留的
  元数据；`deallocate` 读它不违反“不得读写用户已分配内存”的约束。
- `order_flags` 的 cell 下标在分配时写入一次；`FREE_BIT` 在释放时置位；
  `next_free` 可能在下一次分配时被回填一次。
- 从 `PageState.first_` 沿 `next_free` 走到 `SENTINEL`，就能扫描整页的块链：
  带 `FREE_BIT` 的块算已释放，其余算存活。扫描结果用于 debug 与析构时检查未释放
  内存；块链不改变“释放块不重新分配”的策略。

### 4.4 页内分配与对齐

记：

- `P = size_of::<usize>()`；
- `page_cells = page_size / P`；
- `used = state.used_`（cell 下标）；
- `align = max(layout.align(), P)`。

在页锁内（`base_ptr = page.cast::<u8>().as_ptr()`，`page: NonNull<Page>` 带整页 provenance）：

```text
base_addr    = base_ptr as usize                    // 只用于对齐计算
header_start = base_addr + (used + 1) * P            // 预留一个 BlockHeader cell
user_addr    = align_up(header_start, align)
user_off     = user_addr - base_addr
header_off   = user_off - P
header_cell  = header_off / P
data_cells   = ceil(layout.size() / P)
end_cell     = header_cell + 1 + data_cells
```

要求：

```text
header_cell >= used
end_cell <= page_cells
```

然后：

```text
state.used_ = end_cell      // 可能跳过 header 前的对齐空洞
state.live_ += 1
header = base_ptr + header_off
header.order_flags_ = header_cell as u16
header.next_free_ = SENTINEL
if state.first_ == SENTINEL {
    state.first_ = header_cell as u16
} else {
    last_header = base_ptr + state.last_ * P
    last_header.next_free_ = header_cell as u16   // 回填块链后继
}
state.last_ = header_cell as u16
返回 base_ptr + user_off..base_ptr + user_off + layout.size()
```

性质：

- `user_addr` 满足 `layout.align()`，且至少按 `P` 对齐；
- `header` 按 `P` 对齐，`order_flags_` / `next_free_` 可安全读写；
- `header` 紧邻用户块之前，所以 `user_ptr - P` 总是 BlockHeader；
- `page_base` 只需按 `Page` 的对齐（至少 `P`）分配，**不需要按页大小对齐**；高对齐
  通过 `align_up` 在实际地址上完成；
- 所有页内指针都从 `NonNull<Page>` 原始指针偏移，保留整页 provenance；不把整数重新转成指针；
- 对齐填充（`used .. header_cell`）会被 `used_` 跳过，不会被复用。

## 5. 两把锁与 Page 链表

### 5.1 职责划分

| 锁 | 位置 | 保护内容 |
| --- | --- | --- |
| `list_lock_` | `BumpListAlloc` | `Inner.head_` / `Inner.tail_`、`Page.links_.prev_/next_`、挂链/摘链 |
| `Page.lock_` | 每个 Page 头 | `Page.state_.used_/live_/first_/last_`、BlockHeader 的写入与块链回填 |

- `Page` 的 `links_` 与 `state_` 用 `UnsafeCell` 分开，分别由链表锁和页锁保护；两个锁
  保护的是不相交字段。
- `Page` 头不再保存自指指针；页内地址由 `NonNull<Page>` 的原始指针偏移得到。
- `Page.size` / `page_cells` 不存放在 Page 头里：同一 allocator 的所有页大小相同，
  `BumpListAlloc` 保存 `page_size_` 与 `page_cells_`；页内方法把 `page_cells` 作为参数。

### 5.2 锁顺序

允许的嵌套：

```text
list_lock_ -> Page.lock_   // 分配快路径对 tail 做 try_lock；慢路径锁新页
Page.lock_ -> list_lock_   // 空页清理：持页锁确认 live==0，再取链表锁
```

禁止：

```text
持有 list_lock_ 时阻塞等待一个已经共享的 Page 的页锁
```

- 分配快路径在持有 `list_lock_` 时对 tail Page 做 `try_lock`；拿到页锁后立刻释放
  链表锁，再在页锁内 bump。
- 分配慢路径在持有 `list_lock_` 时创建新页并拿它的页锁；新页尚未挂链，没有竞争。
- `try_lock` 失败时释放链表锁，`spin_loop` 后重试；不会持链表锁等待页锁。
- 空页清理（`cleanup_empty_page_`）先取页锁，确认 `live_ == 0`，再取链表锁决定
  “保留 / 挪到 tail / 摘链”。持页锁期间，分配路径的 `try_lock` 会失败并回退，不会形成 ABBA。
- 归还快路径只取页锁；只有页变空后的清理才取链表锁。
- 不再需要 drain：清理路径在摘链/释放前一直持有页锁，新的分配无法在该页上开始。

### 5.3 链表形态

- 双向链表；`head_` / `tail_` 在 `Inner`；
- `tail_` 是链尾，也是分配时优先尝试的页；
- 新页追加到链尾；
- `tail_` 可以是空页：它已经被重置为初始 bump 状态，分配路径可以直接复用它，
  不需要先归还再重新申请；
- 空页会被挪到 `tail_` 保留复用；如果已经有一个空 tail，多出来的空页摘链归还。
  因此链表中最多有一个空 Page，且总是 `tail_`；
- 空页可以出现在链头、链中或链尾，摘链时分别更新相邻指针与 `head_` / `tail_`。

### 5.4 空页复用与归还

- 一个页只有在 `live_` 从 1 减到 0 时才变成空页；
- 最后一个归还者在页锁内把 `used_` / `first_` / `last_` 重置，Page 回到初始 bump 状态；
- 如果这个空页正好是 `tail_`，保留它，不摘链、不归还；下一次分配可以直接复用；
- 如果它不是 `tail_`，`cleanup_empty_page_` 持页锁、再取链表锁：
  - 若当前没有空 tail（`Inner.tail_empty_ == false`），把它从原位置摘下并挪到 `tail_`，
    保留复用；旧 tail 变成非 tail 的存活页；
  - 若已经有一个空 tail，把它摘链并在锁外归还给 backing allocator；
- 空 tail 页不会因为追加新页而变成非 tail：分配路径在空 tail 上分配失败时直接返回
  `AllocError`，不会追加同大小的新页（同大小新页也无法解决容量问题；高对齐失败属于
  该限制）；
- `Inner.tail_empty_` 在链表锁内维护：空页成为 tail 时置真，空 tail 被成功复用时
  清除；
- 清理不需要额外的 `retiring` 标记：页锁本身保证清理期间没有新的分配能在该页上开始；
  非 tail 页本来就不会被分配路径选中；
- 因此 `BumpListAlloc` 始终最多缓存一个空 Page，且这个空页总是 `tail_`。

## 6. 分配算法

### 6.1 零尺寸

`Allocator` 允许零尺寸分配。零尺寸不创建 Page，也不写 BlockHeader：

```text
返回 NonNull::slice_from_raw_parts(
    一个按 layout.align() 对齐的悬垂地址,
    0,
)
```

`deallocate` 遇到 `layout.size() == 0` 直接返回。

### 6.2 快路径：tail 页有空间

```text
loop {
    list_guard = list_lock_();
    tail = inner.tail_;

    if tail 为 None:
        走慢路径（创建新页）;

    page = tail;
    if page.try_lock_() 失败:
        drop(list_guard);
        spin_loop();
        continue;

    drop(list_guard);              // 页锁已拿到，页不会在链表上被摘走
    if page.try_alloc_locked(page, layout, page_cells) 成功:
        drop(page_guard);
        return 块;
    // 空间不足或对齐放不下
    drop(page_guard);              // 必须先放页锁，才能重新取链表锁
    走慢路径;
}
```

- `try_lock` 在持有链表锁时完成；一旦成功，页锁就阻止该页被释放。
- 页锁拿到后释放链表锁，bump 不占链表锁。
- `try_lock` 失败不保留页指针，释放链表锁后重试；避免链表锁被页锁等待拖住。
- `try_alloc_locked` 不再有退休检查；空 tail 页（`used_` 已重置）可以直接复用。
- 如果空 tail 页也放不下这个请求（例如 align 超过页可容纳范围），直接返回
  `AllocError`；不要追加新页，否则唯一空 Page 会变成非 tail。
- 空 tail 被成功复用时，分配路径在返回前重新取链表锁并把 `Inner.tail_empty_` 清零；
  失败时保留空页和标记。

### 6.3 慢路径：追加新页

`try_lock` 竞争失败只重试，不走慢路径。慢路径只用于：tail 为 `None`，或 tail **有
活跃块**但放不下。空 tail 放不下时直接返回 `AllocError`，不追加新页：

0. 先做一次“请求上限”预检查：若
   `ceil(layout.size() / P) > page_cells - PAGE_HEADER_CELLS - 1`，无论怎么对齐都放不下，
   直接返回 `AllocError`，避免无意义地创建新页；
1. 重新取 `list_lock_`；
2. 如果 `tail_` 已经不是刚才观察到的页，释放链表锁并重试（另一个线程可能已经追加了
   可用的新页）；注意只比较指针，不解引用旧指针；
3. 否则在链表锁内：
   - 向 backing allocator 申请 `page_size_` 字节、按 `Page` 对齐的 Page；
   - 初始化 Page 头（`used_ = PAGE_HEADER_CELLS`、`live_ = 0`、`first_ = last_ =
     SENTINEL`、links 为 `None`、页锁为未锁定）；
   - 在新页上完成本次分配（新页尚未挂链，没有竞争）；分配完成后先释放新页的页锁；
   - 把新页追加到当前 `tail_` 之后；`tail_ = new_page`、`tail_empty_ = false`；
   - 释放链表锁并返回新块。
4. 如果新页分配失败（包括单块放不下），释放新页并返回 `AllocError`，链表不变。

慢路径持有链表锁调用 backing allocator；这是 v1 接受的代价。后续可以把“申请新页”
移到链表锁外，再回锁拼接，但需要额外处理重复开页。

### 6.4 新页为什么能放得下

构造 `BumpListAlloc` 时已经检查：

```text
page_cells <= MAX_PAGE_CELLS
page_cells * P == page_bytes
```

单块分配在页内按 4.4 节计算；如果 `end_cell > page_cells`，说明这个请求大于页可容纳
空间，直接返回 `AllocError`，不跨页、不换大页。

## 7. 释放与回收

### 7.1 快路径：页还没空

```text
deallocate(ptr, layout):
    if layout.size() == 0: return;

    header = ptr - P;
    flags = *(header as *const u16);
    cell = flags & ORDER_MASK;
    page_base = header - cell * P;
    page = page_base as *mut Page;

    page.lock_();
    state.live_ -= 1;
    header.order_flags_ |= FREE_BIT;   // 标记已释放，不改块链
    if state.live_ > 0:
        unlock;
        return;                 // 不碰 BumpListAlloc 的链表锁
    // 空页重置：回到初始 bump 状态，可立即复用
    state.used_ = PAGE_HEADER_CELLS;
    state.first_ = SENTINEL;
    state.last_ = SENTINEL;
    unlock;
    cleanup_empty_page(page);   // 保留 tail 空页，或归还非 tail 空页
```

第 2 步在取页锁之前完成是安全的：该块仍然活跃，`live_ >= 1`，页不会被释放；BlockHeader
的 cell 下标与块链后继在分配时写入/回填，`FREE_BIT` 只在本次释放时置位。

页变空后旧块链被丢弃（`first_` / `last_` 重置），因此扫描空页会得到 `(0, 0)`；
Page 头回到初始 bump 状态，下一次分配可以直接复用它。

### 7.2 空页清理：保留一个空 tail

```text
cleanup_empty_page(page):
    page.lock_();                 // 持页锁，阻止新的分配在本页开始
    if page.live_ != 0:
        unlock;
        return;

    lock list_lock_;
    if inner.tail_ == page:
        // 已经是空 tail：保留复用
        inner.tail_empty_ = true;
        unlock list_lock_;
        unlock page.lock_;
        return;

    linked = inner.head_ == page || page.prev_.is_some() || page.next_.is_some();
    if !linked:
        unlock list_lock_;
        unlock page.lock_;
        return;

    unlink(page);                 // 更新 head_/tail_/prev_/next_
    if inner.tail_empty_ {
        // 已有空 tail：这个额外的空页归还
        unlock list_lock_;
        unlock page.lock_;
        dealloc_page(page);
    } else {
        // 还没有空 tail：把这个空页挪到 tail 保留复用
        old_tail = inner.tail_;
        link_after(old_tail, page);
        inner.tail_empty_ = true;
        unlock list_lock_;
        unlock page.lock_;
    }
```

- 页锁在“检查 live、决定保留/挪动/摘链”期间一直持有；分配路径对页锁只做
  `try_lock`，失败会释放链表锁后重试，因此不会与 `Page.lock_ -> list_lock_` 形成
  ABBA，也不需要 drain。
- 页是 tail 时保留；它不是 tail 且当前没有空 tail 时，挪到链尾保留复用；已经有空
  tail 时，多出来的页归还。
- `Inner.tail_empty_` 只在链表锁内读写。空 tail 被成功复用时，分配路径会在返回前
  清除该标记（见 6.2）。
- 空 tail 页不会被追加路径变成非 tail；清理只在最后一个块归还时进入，因此空页只有
  这一条清理路径，不会出现两个清理者同时释放同一页。
- 如果 `linked == false`，说明另一个清理者已经摘链；不重复释放。
- 一个 allocator 因此始终最多缓存 `tail_` 这一个空 Page，超过一个空 Page 时其余都归还。

### 7.3 页在链表中的位置

- 页是链头、链中或链尾时，`unlink` 分别更新 `head_` / `tail_` 与邻居；
- 空页若是 `tail_`，保留复用，不摘链；
- 空页若不是 `tail_` 且没有空 tail，会挪到链尾成为新的 `tail_`；旧 tail 变成非 tail；
- 空页若不是 `tail_` 且已有空 tail，摘链并归还，`tail_` 不受影响；
- 空 tail 页不会因为追加新页变成非 tail；分配路径在空 tail 上失败会直接报错；
- 链表只剩一个空页时，它就是 `tail_`，保留复用；allocator drop 时再统一归还；
- 页内已释放的块不会被复用，只有整页空掉才重置/回收。

### 7.4 `BumpListAlloc` 析构

`Drop` 遍历整条页链，对每个 Page 做一次 `scan_chain_`，然后归还给 backing allocator，
不调用用户数据的析构函数，也不要求 `live_ == 0`。

- 扫描沿 `PageState.first_` → `next_free` → `SENTINEL` 走完块链，统计 live/freed，并
  校验 order、首尾指针与 `live_` 计数；
- 默认 `no_std` 构建只做校验，不输出；
- 开启 `std` 特性（或测试构建）时，如果 `live > 0`，会把未释放块数量写到 stderr；
  链损坏时也会写一条警告；
- 警告通过忽略 I/O 结果的 `writeln!` 完成，不 panic，不改变析构流程。

安全前提：

- 只对 `&BumpListAlloc` 实现 `Allocator`，安全代码中的 `Vec` / `Box` 持有
  `&BumpListAlloc`，借用检查器不允许在它们仍存活时析构 allocator；
- 若用户通过 `mem::forget` 泄漏容器，借用结束，allocator 可以析构；此后不再有安全途径
  访问那些块，释放整页是允许的；
- `Drop` 不与其他安全引用并发，因此不需要取链表锁；`scan_chain_` 会短暂取页锁，
  但此时不存在并发持有者，也不会 drain。

## 8. 并发正确性

### 8.1 分配与归还的锁交互

- 两个分配者可能都从同一个 tail 页分配：它们通过页锁串行化；链表锁只在取尾页和
  `try_lock` 时短暂持有。
- 一个分配者和一个归还者可能同时访问同一页：归还者只取页锁，分配者也取页锁，二者
  在页锁上串行化；链表锁不参与。
- 两个归还者可能同时归还同一页：页锁串行化 `live_` 递减；只有把 `live_` 减到 0 的
  那一个走空页清理。
- 空页清理先取页锁，确认 `live_ == 0`，再取链表锁决定“保留为 tail / 挪到 tail /
  归还”。清理期间页锁阻止新的分配在该页上开始；分配路径只对 tail 做 `try_lock`，
  失败即回退，所以 `Page.lock_ -> list_lock_` 不会形成 ABBA，也不需要 drain。
- 空页挪到 tail 后，分配路径只会从 tail 使用它；旧 tail 变成非 tail 的存活页。
- 已有空 tail 时，多出来的空页摘链后不会有分配路径再选中它；页锁也没有持有者，
  可以安全归还。
- 空 tail 被成功复用时，`tail_empty_` 在链表锁内清除；失败则保留空页并返回
  `AllocError`。

### 8.2 为什么归还快路径不需要链表锁

`BlockHeader.order_flags` 的低 15 位直接给出 block 的 cell 下标，减去 `cell * P`
就得到页首；页是否为空由页锁下的 `live_` 判断。普通归还只取页锁；只有“页已空、
需要决定保留/挪到 tail/归还”这一少数路径才需要 `list_lock_`。因此普通归还的冲突域是
单个 Page。

### 8.3 `Send + Sync`

- `BumpListAlloc<A>` 通过 `unsafe impl` 实现 `Send` / `Sync`，边界分别为
  `A: Send` / `A: Sync`（默认 `A = Global` 两者都满足）。
- `Inner` 与 `Page` 中的 `NonNull` 指针不自动 `Send + Sync`；链表锁、页锁与 `UnsafeCell`
  的字段划分保证可变访问被串行化。
- `&BumpListAlloc<A>` 的 `Allocator` 实现本身不要求 `A: Send + Sync`；若 `A` 不满足
  相应边界，只是失去对应的跨线程能力，单线程使用仍然正确。

### 8.4 不允许 unwind

`Allocator` 的分配/释放方法不应 unwind。实现中：

- 不使用 `unwrap` / `expect`；
- 所有加、乘、减用 checked arithmetic；
- 不加会在正常路径触发的 `assert!`；
- 自旋锁不会失败，`try_lock` 失败走重试；
- `Drop` 只做指针读取与 `deallocate` 调用。

### 8.5 已知代价

- 慢路径在链表锁内调用 backing allocator；若 backing allocator 阻塞，其他链表操作会
  等待。v1 接受这个代价。
- 分配快路径需要在链表锁内做一次页锁 `try_lock`；页锁竞争激烈时会重试，但不会持链表锁
  等待。
- 不要在 `A` 的回调里重入同一个 `BumpListAlloc`；这会造成自死锁。backing allocator
  应当是独立的分配器（默认 `Global`）。

## 9. 公开 API

### 9.1 `PageSize`

```rust
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum PageSize {
    P1K, P2K, P4K, P8K, P16K, P32K, P64K, P128K, P256K,
}

impl PageSize {
    pub const fn bytes(self) -> usize;
    pub const fn cells(self) -> usize; // bytes / size_of::<usize>()
}

pub const MAX_PAGE_CELLS: usize = 1 << 15;
pub const MAX_PAGE_BYTES: usize = MAX_PAGE_CELLS * size_of::<usize>();
```

- `PageSize` 是有限选项，不接受任意 `usize`；
- 所有选项是 2 的幂；
- `P256K` 在 32 位不满足 `cells <= MAX_PAGE_CELLS`，构造时返回
  `UnsupportedPageSize`；
- 当前实现提供全量 1 KiB–256 KiB；如需裁剪集合，只需调整枚举与测试。

### 9.2 `BumpListAlloc`

```rust
pub struct BumpListAlloc<A: Allocator = Global> {
    // 私有字段
}

impl<A: Allocator> BumpListAlloc<A> {
    pub fn new_in(
        alloc: A,
        page_size: PageSize,
    ) -> Result<Self, BumpListAllocError>;

    pub fn page_size(&self) -> PageSize;
}

impl BumpListAlloc<Global> {
    pub fn new(page_size: PageSize) -> Result<Self, BumpListAllocError>;
}

unsafe impl<A: Allocator> Allocator for &BumpListAlloc<A> {
    fn allocate(&self, layout: Layout) -> Result<NonNull<[u8]>, AllocError>;
    unsafe fn deallocate(&self, ptr: NonNull<u8>, layout: Layout);
}
```

- 只有 `&BumpListAlloc` 实现 `Allocator`；`BumpListAlloc` 本身不实现；
- 不实现 `Clone`；`&BumpListAlloc` 是 `Copy`，因为它只是引用；
- `new` / `new_in` 只校验页大小与平台支持，不预先申请 Page；第一次分配才申请；
- 所有 Page 大小相同；`page_size()` 返回配置值；
- 不使用 `PageSize` 之外的页大小参数；
- 默认 `no_std`；可选 `std` 特性只控制 Drop 时的未释放块警告输出，不改变分配语义。

### 9.3 错误类型

```rust
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
#[non_exhaustive]
pub enum BumpListAllocError {
    UnsupportedPageSize { page_size: PageSize },
}
```

- 实现 `core::error::Error` 与 `Display`；
- 分配失败走 `AllocError`，不混入构造错误；
- 如果最终把 `P256K` 从枚举中移除，使所有平台都支持全部选项，构造可以改成不返回
  `Result`，错误类型也可以删除或保留为将来扩展。

### 9.4 使用示例

```rust
use bumplist_alloc::{BumpListAlloc, PageSize};
use std::vec::Vec;

fn demo() -> Result<(), Box<dyn std::error::Error>> {
    let bump = BumpListAlloc::new(PageSize::P4K)?;
    let mut values: Vec<u32, &BumpListAlloc> = Vec::new_in(&bump);
    values.extend_from_slice(&[1, 2, 3, 4]);

    // 注意：`Vec` 增长到超过 4 KiB 页可容纳空间时会得到 AllocError，
    // 标准容器通常会走 handle_alloc_error；这里只演示小块。
    assert_eq!(&values[..], &[1, 2, 3, 4]);
    Ok(())
}
```

`Vec` 的分配器类型是 `&BumpListAlloc`，生命周期由借用关系携带，等价于“不带
`Retain<T>` 的 sw-scope”。

## 10. 关键不变量与安全论证

### 10.1 不变量

1. **所有页同大小**：`BumpListAlloc` 的 `page_size_` / `page_cells_` 对每个 Page 一致。
2. **页地址稳定**：Page 一旦分配就不移动；Page 头在页起始处。
3. **页内不重叠**：`used_` 单调递增；每次分配的 BlockHeader cell、用户块 cell 与之前
   的块不重叠；`used_` 按 cell 推进。
4. **块头有效**：活跃块的 `BlockHeader.order_flags` 低 15 位是 BlockHeader 自身的
   cell 下标；`page_base = header - cell * P` 得到所属 Page。
5. **块链一致**：非空页从 `PageState.first_` 沿 `next_free` 走到 `SENTINEL`，恰好
   访问所有已分配块头；每个块头的 cell 下标等于它所在的 cell，`last_` 是最后一个
   块头；`FREE_BIT` 标记已释放块，`live_` 等于非 Free 块数。空页重置后
   `first_ = last_ = SENTINEL`，扫描得到 `(0, 0)`。
6. **空页条件**：`live_ == 0` 的页一定是 `tail_`，且 `used_ = PAGE_HEADER_CELLS`、
   `first_ = last_ = SENTINEL`，`Inner.tail_empty_ == true`；它是唯一被缓存的空页。
   非 tail 的页 `live_ > 0`。
7. **链表一致**：`head_.prev_ == None`、`tail_.next_ == None`，相邻页的 `prev_` /
   `next_` 互为对方；所有链表修改与 `tail_empty_` 的读写都在 `list_lock_` 内。
8. **字段锁归属**：`links_` 由链表锁保护，`state_` 由页锁保护；Page 头不再保存
   `base_`，所有字段都有明确锁归属。
9. **用户内存不被触碰**：allocator 只读写 Page 头、BlockHeader、`used_` / `live_` /
   块链；不读写 `ptr..ptr + layout.size()`。
10. **对齐**：返回指针满足 `layout.align()`，且至少是 `P` 的倍数。
11. **u16 上限**：`page_cells <= 1 << 15`；`order_flags` 的低位、`used_`、`live_`、
    `first_`、`last_` 均可由 `u16` 容纳。
12. **provenance**：页内指针都从 `NonNull<Page>` 的原始指针偏移；Page 头之外的写入
    不依赖 `&Page` 的 provenance。
13. **C 布局**：`Page`、`PageLinks`、`PageState`、`BlockHeader`、`SpinLock` 都是
    `#[repr(C)]`；`Page` 字段按大小降序手动编排。

### 10.2 `unsafe impl Send + Sync`

理由：

- 链表与 `links_` 由 `list_lock_` 串行化；
- 页状态由页锁串行化；
- Page 地址稳定；BlockHeader 的 cell 下标不变，`next_free` 只在下一次分配时回填、
  `FREE_BIT` 只在释放时置位，这些修改都在页锁内完成；
- 用户内存由用户按借用规则独占访问；
- `A` 的线程安全由 `Send` / `Sync` 边界约束。

### 10.3 provenance 与指针运算

- `deallocate` 从用户指针减去 `P` 读取 BlockHeader，再减去 `cell * P` 得到 Page 首址；
  这些地址都落在同一页分配内，指针 provenance 来自整页分配。
- BlockHeader 是 allocator 预留的 cell，不是用户块的一部分。
- **不再保存 `base_` 指针**。页内方法额外接收 `page: NonNull<Page>`；用户块与
  BlockHeader 从 `page.cast::<u8>()` 偏移写入。`&Page` 只用于访问 Page 头内的锁/
  状态/链接，不用它的 provenance 写 Page 头之外的内存。这是 Miri Stacked Borrows
  要求的安全做法，同时不占额外指针空间。
- 对齐计算可以临时把地址转成 `usize`，但创建页内指针时一律用 `page.cast::<u8>().add(offset)`
  保留 provenance；代码中不存在“整数重新转成指针”的路径（零尺寸的悬垂指针使用
  `NonNull::without_provenance`）。
- 失败 `try_lock` 的分配线程必须丢弃 page 指针，不能保留到链表锁释放之后再使用。
- Miri 已在 `-Zmiri-strict-provenance` 下通过全部单元/集成/并发测试。

### 10.4 `Allocator` 契约

- 返回块大小恰好为 `layout.size()`（不故意 overallocate）；
- 块之间不重叠，且不跨页；
- `allocate` / `deallocate` 不读写用户块内容；
- `deallocate` 接受同一 `layout`（或 fit 的 layout）；
- 不 unwind；
- 零尺寸返回按对齐的悬垂指针；
- 页被释放时，所有指向它的合法块都已经 `deallocate`（或 allocator 正在析构，安全
  借用已经结束）。

## 附：`denco_arena` 特性（2026-11-16 21:20）

`mptp_rpc` 的 allocator 重构需要 `MpDecoder::new_in` 把字符串与头表分配进会话持有的
`BumpListAlloc`。为此增加一个**可选**特性 `denco_arena`：

- 依赖 `abs_denco`（`default-features = false`，只取 `TrArena` / `TrArenaBytes`）；
- `impl TrArena<'alloc> for BumpListAlloc<A>`：`Ref<T> = BumpListBox<'alloc, T>`，
  一个拥有 `T` 的特制 Box；分配走既有的 `Allocator for &BumpListAlloc`，析构时先
  `drop_in_place`，再从块头反推 `Page` 并调用 `Page::release_page_` 归还块；
- `impl TrArenaBytes<'alloc>`：把源字节拷进 arena，返回 `&'alloc [u8]`；
- 新错误 `BumpListArenaError`：`AllocError` 不实现 `core::error::Error`，这里提供薄适配。

安全不变量：`BumpListBox` 独占一块按 `Layout::new::<T>()` 分配的内存，析构时运行
`T` 的析构函数，并通过 `BlockHeader` 的 cell 下标 O(1) 反推所属 `Page`，调用
`Page::release_page_` 归还块；块只归还一次。零尺寸 `T` 没有 `BlockHeader`，只运行析构，
不碰 `Page`。`TrArenaBytes` 交出的是借用切片，字节没有 Drop 语义，随分配器析构释放。

注意：`Page::release_page_page_` 负责「块 → 页」的归还与空页重置；若页变空，它通过 owner
指针直接调用 `BumpListCore::cleanup_empty_page_`，因此「摘链 / 交还底层分配器」也在
`BumpListBox` 的析构路径里完成。

单块仍受页大小上限约束：超过页容量的请求返回 `BumpListArenaError`。

## 附：Page owner、BumpListCore 与页锁（2026-11-16 22:30）

`BumpListBox` 归还块时不应该持有 `BumpListAlloc` 引用；需要知道 owner 的是 **Page**。
但 Page 也不应该保存 `A` 泛型或每个 Page 一份函数指针。最终形状：

```rust
pub struct BumpListAlloc<A: Allocator = Global> {
    core_: BumpListCore, // 非泛型，内联；Page 的 owner 指向它
    alloc_: A,           // 声明在 core_ 之后，core 先析构
}

pub(crate) struct BumpListCore {
    page_size_: PageSize,
    page_cells_: u16,
    page_bytes_: usize,
    list_lock_: SpinLock,
    inner_: UnsafeCell<Inner>,
    backing_alloc_: PageAllocFn,   // unsafe fn(*const Core, Layout) -> ...
    backing_dealloc_: PageDeallocFn,
}

pub(crate) struct Page {
    links_: UnsafeCell<PageLinks>,
    state_: UnsafeCell<PageState>,
    owner_: AtomicPtr<BumpListCore>, // 最低位兼作页锁
}
```

- `BumpListCore` 与 `A` 无关；`Page` 的 owner 指向它，`BumpListBox<'alloc, T>` 不需要
  `A` 参数。
- 真正需要 `A` 的建页 / 还页通过 Core 里的两个单态化函数指针完成；Core 保存一个整
  分配器自指针，函数用 `offset_of!` 取出 `alloc_`。不再每个 Page 保存函数指针，也没有
  `Box<A>`。
- **owner 指针最低位就是页锁**：Core 至少按指针宽度对齐，最低位必为 0；
  `lock_` / `try_lock_` 用 `AtomicPtr` 的 CAS 与 `map_addr` 置位 / 清位，保留 provenance。
  Page 头因此仍是 64 位 32 字节（4 cells）、32 位 20 字节（5 cells）。
- `Page::release_page_page_`：持页锁归还块；若 `live_ == 0`，先释放页锁，再直接调用
  `BumpListCore::cleanup_empty_page_`，完成「保留 tail / 挪到 tail / 摘链归还」。
- `BumpListCore` 与 `A` 都内联；Core 先析构、A 后析构。函数指针用 `offset_of!` 从
  Core 保存的整分配器自指针取出 A，因此没有 `Box<A>`；自指针在每次操作前刷新。
- 地址稳定性：创建第一个 Page 后 `BumpListAlloc` 不能移动；需要移动时先 `Box::new`。
  Page 的 owner 指向内联 Core。
- `BumpListAlloc::deallocate_` 不再自己调用 `cleanup_empty_page_`：升级逻辑统一在
  `Page::release_page_page_`；`BumpListBox::drop` 与普通 `deallocate` 走同一条回收路径。

`denco_arena_box_release_returns_block_` 验证 `TrArena` 句柄析构后 live 回到 0，且唯一
空页仍保留为 tail；Miri strict-provenance 覆盖 Core/Page/backing 的整个路径。
