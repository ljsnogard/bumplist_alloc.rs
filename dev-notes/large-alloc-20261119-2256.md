# 超过页大小的分配：单块大页设计

- 状态：**已实施（2026-11-19，分支 `feat/big-page`；`big_page` 默认关闭）**
- 日期：`2026-11-19 22:56`（同日实现并补性能对比）
- 相关代码：[`src/alloc_.rs`](../src/alloc_.rs)、[`src/page_.rs`](../src/page_.rs)、
  [`src/init_page_.rs`](../src/init_page_.rs)、[`src/boxed_.rs`](../src/boxed_.rs)
- 结论：**能做到，而且可以几乎完全复用现有的“块头 → Page → 页锁 → `returned_ ==
  used_` → 空页回收”机制**。推荐把一次超页分配做成一个**只放一个块的专用 Page**
  （下文称“大页”），用 `BigPage` 扩展头记录它自己的 backing 布局；大页放入
  `BumpListCore` 中独立的大页链表 `BigPageList`，与普通页链表 `inner_` 完全分离，
  因此永远不会成为 `tail_`，块释放后整页立即摘链归还，不进入“最多缓存一个空页”的
  小页策略。小页的 `Page`、`BlockHeader`、`PageState` 与分配 / 释放快路径都保持
  不变。

> 实现已落在 `feat/big-page` 分支；`big_page` 默认关闭，关闭时行为与旧版一致。
> 开启 feature 会把“超页请求由 `AllocError` 改为成功”，属于对外可见的行为变化；
> 是否默认开启仍应按 [`AGENTS.md`](../AGENTS.md) 第 1 条由团队确认。

## 1. 现状与问题分解

### 1.1 小块是如何完成回收的

非零尺寸的小块在分配时：

```text
Page base
├── Page 头                     // base_ / cells_ / used_ / returned_ / owner(锁位)
├── BlockHeader (cell index = base_)
├── [对齐 padding / locator]
├── 用户块
└── ...
```

`Allocator::deallocate(ptr, layout)` 与 `Box::drop` 都走同一条路径：

1. 读取 `ptr - P` 处的 cell：
   - 最高位为 0：它是活跃块头，低 15 位就是块头自身的页内 cell 下标；
   - 最高位为 1：它是 locator，低 15 位是到块头的距离；
2. `page = header - order * P`，O(1) 得到页首；
3. 取页锁，`Page::release_locked_` 校验块头、把 `FREE_BIT` 置位，并按
   `next_free_ - header_cell` 把本块 cell 数累加到 `returned_`；
4. `returned_ == used_` 时把 `used_` / `returned_` 归零，表示整页已空；
5. `Page::release_page_` 通过 `Page.owner_` 找到 `BumpListCore`，由
   `cleanup_empty_page_` 在链表锁下决定“保留唯一空页 / 挪到 tail / 摘链归还”。

这条路径有三个关键性质：

- 反查只需要用户指针，不需要分配器句柄，因此 `Box`（只保存 `NonNull<T>`）也能归还；
- 反查 O(1)，快路径只取页锁，不碰链表锁；
- 页是否归还由页自己的 `returned_ == used_` 决定，页是回收决策的最小单位。

### 1.2 现有硬约束

`BlockHeader` 只有 `PTR` 字节（64 位 8、32 位 4），其中两个 `u16` 分别保存：

```text
order_flags_:  低 15 位 = 块头自身的页内绝对 cell 下标；最高位 = FREE_BIT
next_free_:    本块末尾（下一个块头 / bump 末尾）的页内绝对 cell 下标
```

因此：

- 页内 cell 数必须 ≤ `MAX_PAGE_CELLS = 1 << 15`；
- 块头的 cell 下标、块的结束 cell 都必须能用 15 位表示；
- `PageSize` 的最大值因此是 `MAX_PAGE_CELLS * P`（64 位 256 KiB，32 位 128 KiB）。

`PageState` 的四个字段也都是 `u16`。如果直接把“页变大”到超过 256 KiB，`cells_` /
`used_` / `returned_` 与 `BlockHeader` 都会溢出。

### 1.3 真正要解决的三个子问题

超页分配不是“向 backing 多要一块内存”这么简单，必须同时回答：

1. **返回的指针必须是连续可用的**：`Allocator::allocate` 返回 `NonNull<[u8]>`，调用方
   按一个连续切片使用（`Vec`、`Box`、`denco` 的字节切片都是如此），不能是多个不连续
   页拼起来。
2. **释放时如何 O(1) 找回归属**：`Box::drop` 只有用户指针，没有 `layout`，也没有
   arena 句柄。必须像小块一样，从用户指针附近的内嵌元数据直接找回 Page / Core。
3. **谁来判断何时把内存还给 backing / 系统**：小块靠页的 `returned_ == used_`；
   大块也必须有一个等价的“页级”判据，否则要么泄漏，要么需要全局注册表或线性扫描。

## 2. 候选方案

### D1 单块大页 + 复用现有 Page 状态机（推荐）

每个超页请求单独申请一块 backing 内存，在其中构造一个**只放一个块**的 Page：

```text
raw ──────────────────────────────────────────────►
│ 前缀（因用户指针对齐而浪费，< align） │ BigPage 头 │ BlockHeader │ 用户块 │
                                      ▲              ▲             ▲
                                     base           base+h        base+h+1
```

- `base` 是 Page 首地址，`BigPage` = `Page` + 自己的 backing 布局；
- `PageState.base_ = h`（`h = ceil(size_of::<BigPage>() / P)`）、`cells_ = 1`、
  `used_ = 1`、`returned_ = 0`；
- 块头就在 `base + h * P`，用户块紧跟在它后面，**两者之间没有 padding**；
- 块头 `order_flags_ = h`、`next_free_ = h + 1`，于是现有 `release_locked_` 计算出的
  span 正好是 1，`used_ == returned_` 后整页归零，和一个小块完全一样；
- `locate_block_` 不需要任何改动：用户块前一 cell 就是块头，`order = h`，
  `page = header - h * P = base`。

这样，**15 位下标描述的是“块头在页内的位置”，不是“块有多大”**。大页的块头位置仍然
只有 `h`（64 位约 7，32 位约 8），完全放得下；用户块的巨大尺寸由 `BigPage` 里的
`usize` 记录，不进入 `BlockHeader` / `PageState`。

大页不参与小页的分配候选：它挂在**独立的 `BigPageList`** 上，`tail_` 始终是普通页，
因此小分配永远不会选择它。释放时 `cleanup_empty_page_` 识别出大页，直接摘链并按存储的布局归还
backing，不缓存。

### D2 全局加宽 BlockHeader / PageState

把 `order` 改成 `u32` / 字节偏移，把 `next_free`、`cells_`、`used_`、`returned_` 全部
加宽。

- 优点：概念最直接，页大小上限可以提高到 4 GiB 级。
- 缺点：`BlockHeader` 会从一个 cell 变成两个 cell，**每个小块都多付一个指针宽度**；
  `PageState` 从 8 字节变大，`Page` 头随之变大；`try_alloc_locked_` / `release_locked_`
  / `scan_chain_` / locator 编码全部要重写。为少数大块牺牲所有小块，与“不影响小内存
  分配”的目标冲突。
- 结论：拒绝。

### D3 连续多页 run（每页一个 Page 头）

申请 `N * page_size` 的连续内存，在其中放 N 个 Page 头，让一个用户块跨越它们。

- 页头会落在用户块内部，破坏用户数据；如果只在第一页放页头、后面不再放，那么它本质
  上就是 D1，只是“页大小”等于 `N * page_size`。
- 结论：D1 已经覆盖这个想法；单独实现 D3 只会多一套几何计算。

### D4 分段页 / scatter-gather

把大块拆成多个不连续页，用段表拼接。

- `Allocator` 契约要求返回一个连续的 `[u8]`，`Vec` / `Box` / `Deref` 都假定连续。
- 若改成自定义的“大对象”类型（段表 + 自定义 Deref），会引入与标准 `Allocator` 不兼容
  的第二套 API，且 `Box<'a, T>` 无法透明支持。
- 结论：超出本 crate 的 `Allocator` 定位，拒绝。

### D5 直接向 backing 透传 + 前缀头

不创建 Page，直接在用户块前放一个 `LargeHeader`，记录 `core`、`layout`、链表指针。

- 释放时需要区分“这是小块还是大块”，而小块的前一 cell 是 `u16` 编码的块头 / locator；
  如果大块前缀也用同一 cell，就需要一个不会与小块编码冲突的 tag。小块头部的
  `_reserved_` 目前并未初始化，直接读整个 `PTR` 字会读到未初始化内存；32 位平台更
  没有余量。
- 仍然需要一张表把所有大块挂起来，否则 arena 析构时无法释放仍然存活的大块；这张表
  要么放进 `Core`（增加一个指针），要么用全局结构（锁竞争、`no_std` 不可行）。
- 还要自己维护“大块是否已释放”的计数与并发协议。等于把 Page 已经做好的事情重做一遍。
- 结论：只有在完全不想碰 `Page` 时才考虑；本设计不需要。

### D6 out-of-band 注册表

用一个全局 / Core 内的哈希表记录 `用户指针 → 大块描述`。

- 释放快路径要取全局锁或做哈希，破坏“归还只需要页锁”的性质；
- `no_std` 且无外部依赖的约束下要自己实现表；
- 与 `Box` 的无句柄释放路径不匹配。
- 结论：拒绝。

### D7 只调大 `PageSize` / 继续返回 `AllocError`

- 任何固定页大小都有上限；调大到 1 MiB 仍然无法分配 2 MiB；
- 所有小对象都被迫进入大页，内部碎片与 `Page` 头开销都上升；
- 不满足“任意请求只要 backing 能提供就应成功”的目标。
- 结论：只能作为过渡，不是解决方案。

### 方案对比

| 方案 | 小块额外开销 | 释放是否 O(1) | 是否需要新全局结构 | 复用现有块链 | 任意大小 |
| --- | --- | --- | --- | --- | --- |
| **D1 单块大页** | 无 | 是（页锁） | 否 | 完全复用 | 只受 backing 限制 |
| D2 全局加宽 | 每块 +1 cell | 是 | 否 | 需重写 | 受新位宽限制 |
| D3 连续多页 run | 无 | 是 | 否 | 部分 | 是（但等于 D1） |
| D4 分段页 | 无 | 是 | 是（段表） | 否 | 是，但非 `Allocator` |
| D5 透传 + 前缀头 | 无 | 是 | 是（大块表） | 否 | 是 |
| D6 注册表 | 无 | 哈希 / 锁 | 是 | 否 | 是 |
| D7 调大页 / 拒绝 | 无 | 是 | 否 | 是 | 否 |

## 3. D1 详细设计

### 3.1 元数据类型

新增一个模块（例如 `src/big_page_.rs`）：

```rust
/// 大页头部之后、用户块之前的扩展元数据。
#[repr(C)]
pub(crate) struct BigPage {
    /// 必须是第一个字段，偏移 0。
    pub(crate) page_: Page,
    /// backing 分配返回的原始指针（可能早于 base，见几何部分）。
    pub(crate) raw_: NonNull<u8>,
    /// 申请 / 归还 backing 时使用的 size。
    pub(crate) alloc_size_: usize,
    /// 申请 / 归还 backing 时使用的 align。
    pub(crate) alloc_align_: usize,
}

/// 大页 Page 头占用的 cell 数（h）。
pub(crate) const BIG_PAGE_CELLS: usize =
    core::mem::size_of::<BigPage>().div_ceil(PTR);
```

- `Page` 必须在偏移 0，这样 `NonNull<BigPage>` 与 `NonNull<Page>` 同址；
- 64 位：`Page` 32 字节 + 3 个 `usize` = 56 字节，`h = 7`；
- 32 位：`Page` 20 字节 + 3 个 `usize` = 32 字节，`h = 8`；
- 编译期断言 `offset_of!(BigPage, page_) == 0` 与 `h + 1 <= MAX_PAGE_CELLS`。

### 3.2 kind 标记

需要让 `cleanup_empty_page_` / 析构路径知道某个 Page 是大页。**不增加 `Page` 的
大小**，复用 `Page.owner_` 现有的标记字：

```rust
const LOCK_BIT: usize = 1;       // 已有：页锁
const LARGE_BIT: usize = 1 << 1; // 新增：大页
const PAGE_TAG_MASK: usize = LOCK_BIT | LARGE_BIT;
```

`Page.owner_` 指向的 `BumpListCore` 至少按指针宽度对齐（`P >= 4`），低两位必为 0，
所以 bit1 可以安全地作为 kind 标记。

需要同步修改的点很少，但必须全部审计：

- 新增 `Page::init_in_place_with_tag_`（`init_in_place_` 以 tag 0 转发），写入
  `owner | tag`；初始化时断言 `owner.addr() & PAGE_TAG_MASK == 0`；
- `Page::owner_ptr_` 的掩码从 `!LOCK_BIT` 改为 `!PAGE_TAG_MASK`；
- `Page::try_lock_` / `PageGuard::drop` 仍然只操作 `LOCK_BIT`，CAS / `fetch_and`
  会保留 `LARGE_BIT`；
- 新增 `Page::is_large_()`：读取 `owner_` 并测试 `LARGE_BIT`；kind 在构造后不再变化，
  可以用 `Relaxed`（也可用 `Acquire` 与锁语义保持一致）。

不选“用 `PageState.cells_ == 1` 隐式判断”的原因：它虽然零改动，但依赖“普通页容量
永远 ≥ 2”这个容易被后续修改破坏的隐含不变量；显式 tag 更安全，且没有空间代价。

### 3.3 几何：用户指针优先，块头紧贴用户块

设：

```text
P   = size_of::<usize>()
h   = BIG_PAGE_CELLS
A   = max(layout.align(), P)          // 用户块至少按指针宽度对齐
raw = backing.allocate(size = (h+1)*P + layout.size() + (A-1), align = A)
```

然后**先确定用户块地址，再由它反推 Page 首地址**：

```text
user = align_up(raw + (h+1)*P, A)
base = user - (h+1)*P
```

这样：

- `user` 满足 `layout.align()`（`A >= layout.align()`）；
- `base` 是 `P` 对齐的：`user` 是 `A` 的倍数，`(h+1)*P` 是 `P` 的倍数；
- `base >= raw`，因为 `user >= raw + (h+1)*P`；
- 用户块紧跟块头：块头位于 `base + h*P`，用户块位于 `base + (h+1)*P`；
- 块头自身的 cell 下标就是 `h`，远小于 `MAX_PAGE_CELLS`，**对齐 padding 再大也不会
  撑大这个下标**。这是本设计能复用 15 位编码的关键。

容量校验：

```text
user + layout.size()
  <= raw + (h+1)*P + (A-1) + layout.size()
  = raw + alloc_size
```

所有加法都用 `checked_add` / `checked_mul`；`alloc_size` 与 `A` 交给
`Layout::from_size_align` 校验，溢出或非法布局返回 `AllocError`。

> provenance 注意：`user` 必须用 `raw.add(offset)` 得到，`offset` 由
> `align_up(raw.addr() + (h+1)*P, A) - raw.addr()` 计算；不能把地址转成 `usize`
> 再转回指针，否则会丢失 provenance，Miri `-Zmiri-strict-provenance` 会报错。
> `base` 同理用 `user.sub((h+1)*P)` 得到。

### 3.4 初始化

在刚申请、尚未共享的内存上：

1. 用 `(h+1)*P` 字节的 slice（`base` 起）调用
   `Page::init_in_place_with_tag_(mem, core, h, LARGE_BIT)`：
   - `page_cells = (h+1)`，`first = h`，于是 `cells_ = 1`；
   - `used_ = 0`、`returned_ = 0`；
2. 写 `BigPage` 的三个字段：`raw_`、`alloc_size_`、`alloc_align_`；
3. 在 `base + h*P` 写 `BlockHeader`：
   - `order_flags_ = h`（`FREE_BIT` 为 0）；
   - `next_free_ = h + 1`；
4. 在持有页锁（或独占初始化阶段）把 `PageState.used_` 设为 `1`；
5. 取链表锁，把大页追加到 `big_` 链表尾部（见 3.5）。

初始化完成后，用户块的数据区（`user .. user + size`）由调用方写入；页头、块头与
`BigPage` 元数据都位于 `[base, base + (h+1)*P)` 内，互不重叠。

传给 `Page::init_in_place_` 的 `mem` 长度是 `(h+1)*P`，**不是**整个 backing 分配。
这带来一个有用的隔离：

- 通过链表里的 `NonNull<Page>` 进行的所有页级访问（`state_`、块链、`BigPage`
  字段）都落在 `[base, base + (h+1)*P)` 内，provenance 由该 slice 覆盖；
- 用户数据只通过 `user` 指针访问，provenance 来自 backing 返回的 `raw`，覆盖整个
  分配；
- 归还 backing 时使用 `BigPage.raw_` 与原始布局，不需要从 `Page` 指针反推 `raw`。

`locate_block_` 返回的 Page 指针是由 `user`（完整分配 provenance）减去偏移得到的，
同样落在分配内；它只用于读取 `PageState` 与块头，不会越界访问数据区。

**注意 `cells_ = 1` 的语义**：它不再表示“整页容量”，而表示“本页在页级记账中只登记
一个 cell”。这是大页的核心约定：

```text
页级记账范围： [base, base + (h+1)*P)   // Page 头 + 块头
数据范围：     [user, user + size)      // 由 BigPage.alloc_size_ 记录
```

`used_` / `returned_` / `next_free_` 只描述前者；后者只用于 backing 的申请与归还。
普通页没有这种分离，因此必须严格保证大页永远不会被小分配路径选中。

### 3.5 链表：独立的 BigPageList

小页链表 `inner_` 与 `tail_` 的语义完全不变。大页使用 `BumpListCore` 中新增的

```rust
#[cfg(feature = "big_page")]
big_: UnsafeCell<BigPageList>,
```

由同一把 list lock 保护。`BigPageList` 复用 `PageList` 的双向结构（`head_` / `tail_` +
`PageLinks`）：

- 分配大页后在链表锁内 `link_after_(big, big.tail_, page)` 追加；
- 释放大页时在链表锁内 `unlink_(big, page)` 摘除，随后立即归还 backing；
- 两条链表不共享节点，`tail_` 永远只指向 root 或普通页；
- 小页的 `cleanup_empty_page_`、`link_after_`、`unlink_` 与空页策略都不需要知道大页
  存在。

代价：开启 feature 时 `BumpListCore` 多两个指针，`InitPage<A>` 随之变大，第一页可用
容量减少 2 个 cell。这个代价只出现在 feature 开启时；关闭 feature 时字段不存在，
`BumpListCore` / `InitPage` 布局与旧版一致。容量检查本来就是按 `InitPage<A>::CELLS`
动态计算的，因此不需要硬编码调整。

为什么不在同一个链表：若把大页插到 `inner_` 的头部，所有遍历（析构、debug 扫描）
与 `tail_` / 空页策略都要按 kind 分支；独立链表把“小页热路径”和“大页生命周期”
彻底分开，代价只是一个冷路径上的 Core 字段。

### 3.6 分配路径

`BumpListCore::allocate_` 只在最前面增加一个分支：

```rust
if layout.size() == 0 { return zero_sized_(layout.align()); }
if !self.fits_page_(layout) {
    return self.allocate_big_(layout);   // 原来这里返回 Err(AllocError)
}
// 原有小页路径完全不变
```

`fits_page_` 仍是现在的保守判断：

```text
layout.size().div_ceil(PTR) <= page_size.cells() - (Page::CELLS + 1)
```

也就是说，只有“数据 cell 数超过普通页最大可用数据 cell 数”的请求才走大页。
“尺寸放得下、但对齐放不下”的请求仍按现有策略返回 `AllocError`（见第 4 节待决事项）。

`allocate_big_` 的步骤：

```text
1. BigGeometry::new(layout)：计算 h、alloc_size、alloc_align；溢出 / 非法 → AllocError
2. 取 backing lock，调用 A.allocate(Layout::from_size_align(alloc_size, align))
3. 计算 user / base（见 3.3）
4. 原地初始化 Page、BigPage、BlockHeader、used_ = 1
5. 取 list lock，把大页追加到 big_ 链表尾部
6. 返回 NonNull::slice_from_raw_parts(user, layout.size())
```

- backing 调用不持链表锁，避免长时间占用；
- 初始化发生在挂链之前，没有并发访问；
- 挂链不会失败；`place_` 返回 `None`（地址运算溢出，理论上不可达）时会先归还刚申请
  的 `raw` 再返回 `AllocError`，不会泄漏；
- `allocate_big_` 的其它失败只可能发生在第 1、2 步，此时还没有 Page 需要清理。

### 3.7 释放路径：与小块完全同构

`Allocator::deallocate` 与 `Box::drop` 都不需要改动：

```text
locate_block_(user) -> (page, header_cell = h)
release_page_(page, h)
```

逐行对照现有 `release_locked_`：

```text
base        = state.base_        = h
cells       = state.cells_       = 1
used        = state.used_        = 1
end         = base + used        = h + 1
header      = base + h * P       = 块头
flags       = order_flags_       = h       （FREE_BIT 为 0）
next        = next_free_         = h + 1
span        = next - header      = 1
returned_  += 1                  = 1       == used_
→ used_ = 0; returned_ = 0; 返回“页刚刚变空”
```

所有范围校验都通过：`header_cell < MAX_PAGE_CELLS`、`header_cell >= base`、
`next > header_cell`、`next <= end`。**不需要给 `release_locked_` 加任何大页分支**。

同样，`scan_chain_` 也无需分支：

```text
base = h, cells = 1, used = 1, end = h+1
从 cell h 走到 h+1，读到一个块头，order = h，next = h+1
存活块数 = 1（未释放）或 0（已释放且 used_ 归零）
```

因此 debug 扫描、析构时的“未释放块”警告都继续有效。

> **语义提醒**：在大页上，`BlockHeader.next_free_` / `PageState.used_` 表示的是
> “页级记账范围的末尾”，**不是用户块的数据末尾**；用户块的真实大小只记录在
> `BigPage.alloc_size_` 里。任何代码都不应把 `next_free_ - order` 当作大块的字节
> 大小。之所以可以这样拆分，是因为大页永远只有一个块，而且它永远不会进入小页的分配
> / 复用路径；页级字段只用于“这个块是否已归还”这一件事。

`locate_block_` 也无需修改：块头紧贴用户块，`order = h`，`page = header - h*P = base`。
`Box` 不需要知道 layout、不需要知道 arena 类型，也不需要大页标记。

### 3.8 空页回收

`Page::release_page_` 在页刚变空时通过 `owner_` 调用
`BumpListCore::cleanup_empty_page_`。该入口只做一次 kind 分流，然后进入各自的清理
函数：

```rust
pub(crate) fn cleanup_empty_page_(&self, page: NonNull<Page>) {
    if page.is_large_() {
        self.cleanup_empty_big_page_(page);
        return;
    }
    // 下面全部是现有的小页 / root 策略，保持原样。
}
```

`cleanup_empty_big_page_` 仍然按“链表锁 → 页锁”取锁，确认
`empty_locked_()` 后从 `big_` 链表 `unlink_`，释放两把锁，再立即归还 backing。
大页不进入小页的 `inner_` 链表，也不会被挪到 `tail_`。

`dealloc_big_page_`：

```rust
fn dealloc_big_page_(&self, page: NonNull<Page>) {
    // SAFETY: 大页已摘链，调用方独占；BigPage 头在 [base, base + h*P) 内。
    let (raw, layout) = unsafe { BigPage::dealloc_parts_(page) };
    let _guard = self.lock_backing_();
    // SAFETY: raw/layout 来自本 allocator 的 backing，且只归还一次。
    unsafe { self.backing_.as_ref().deallocate(raw, layout) };
}
```

策略选择：

- **大页不做“最多缓存一个空页”**。大块尺寸差异大，缓存一个空大页会长期占住可达
  数 MiB 的内存；而且下一次请求未必是同一 `(size, align)`。直接归还让 `Vec` 增长时
  的“申请新缓冲 → 拷 → 释放旧缓冲”及时把旧内存还给系统。
- 如果将来确实需要缓存，可以只缓存**最后一个、且 `(alloc_size, alloc_align)` 完全
  相同**的大页，命中时才复用；这不会影响小页，也不影响本文其余不变量。属于后续优化，
  不在本次范围。

### 3.9 析构路径

`BumpListAlloc` 的最后一个句柄调用 `InitPage::drop_in_place_` →
`BumpListCore::free_non_root_pages_`。它先按原逻辑遍历 `inner_`（root + 普通页），
再单独遍历 `big_`：

```rust
// 普通页：原有循环保持不变。
// 大页：取 big_.head_，逐个读取 next_ 与 scan_chain_，最后 dealloc_big_page_。
let mut cursor = big.head_.take();
big.tail_ = None;
while let Some(page) = cursor {
    let next = page_ref.next_();
    let scan = page_ref.scan_chain_(page);
    // std 特性下按 scan 输出未释放块警告。
    self.dealloc_big_page_(page);
    cursor = next;
}
```

- `next` 必须在归还当前页之前取出；
- `scan_chain_` 对大页返回 `(1, 0)` 或 `(0, 0)`，`std` 特性下的“存在未释放块”警告
  照常输出；
- 大页的归还发生在 `Core` 销毁之前，此时 `A` 仍然有效；
- 遍历结束后仍然清空 root 的 `prev_` / `next_`，避免悬垂链接。

因为两条链表分离，小页循环不需要任何 kind 判断，`free_non_root_pages_` 的大页部分
也不会影响 root 的回收逻辑。

### 3.10 锁与并发

沿用现有三把锁：

- **页锁**：保护 `PageState` 与块头。大页在释放时只需要页锁；页变空后再升级到
  `cleanup_empty_big_page_`。
- **链表锁**：同时保护 `inner_` 与 `big_` 的 `head_` / `tail_` / `links_`。大页的
  追加与摘链都在链表锁内。
- **backing lock**：串行化对 `A` 的 `allocate` / `deallocate`。大页的申请与归还都在
  该锁内。

锁顺序保持“链表锁 → 页锁”，backing lock 不与其它锁嵌套（`dealloc_big_page_` 在
释放 list / page 锁之后才取 backing lock）。因此不会引入新的 ABBA 风险。

大页本身只有一个块，不可能有两个线程同时在同一大页上分配；释放者也唯一。唯一可能的
竞争是“最后一个块释放”与“arena 析构”，但后者要求句柄引用计数归零，而存活的块必然
带着 `'a` 借用或 `Box` 句柄，合法使用下不会并发发生。

### 3.11 不变量与 unsafe 论证

实现时必须写出并校验以下不变量：

1. **位置**：大页只挂在 `big_` 链表上，从不进入 `inner_`；`tail_` 永远不是大页。
2. **记账**：大页的 `PageState` 恒为 `base_ = h`、`cells_ = 1`、`used_ ∈ {0,1}`、
   `returned_ ∈ {0,1}`，且 `returned_ <= used_`。
3. **几何**：`BlockHeader` 位于 `base + h*P`，用户块位于 `base + (h+1)*P`，两者紧邻；
   `next_free_ = h+1 = base_ + used_`。
4. **元数据**：`BigPage.raw_ / alloc_size_ / alloc_align_` 在挂链前写入，之后不再
   修改；它们恰好描述 backing 的原始布局。
5. **tag**：`owner_` 的 bit0 是页锁、bit1 是大页标记；除
   `try_lock_` / `PageGuard::drop` 只碰 bit0 外，所有读取 owner 的地方都要用
   `PAGE_TAG_MASK` 去掉两位。
6. **回收**：大页只能在 `cleanup_empty_big_page_` 或 `free_non_root_pages_` 的大页
   循环中、且已摘链后归还一次；它不进入“空页缓存”，不会在归还后被重新分配。
7. **provenance**：`base` / `user` 都由 backing 返回的 `raw` 通过指针偏移得到；
   `BigPage.raw_` 保存的是带完整 provenance 的原始指针；任何“地址 ↔ 整数”的转换
   只用于计算偏移，不用来重建指针。

逐条对应 unsafe 位置：

- `locate_block_` 读取 `user - P`：用户块来自本分配，前一个 cell 必然是已写入的
  `BlockHeader`；`order = h` 是初始化时写入的，`header - h*P` 落在同一分配内。
- `release_locked_` 的泛型路径：所有 cell 下标都经过上述范围校验，且
  `header_at_(page, h)` 位于 `[base, base + (h+1)*P)` 内。
- `dealloc_big_page_`：`raw` / `layout` 与 `allocate_big_` 完全一致，且调用发生在
  摘链之后；`BigPage` 字段在归还前读取完毕。
- `free_non_root_pages_`：析构期间独占，`next` 先读后还；大页与普通页分别使用正确的
  布局。
- `Page::owner_` 的 tag 操作：`map_addr` 保留 provenance；Core 对齐保证 bit0 / bit1
  可用。

### 3.12 为什么小内存路径不受影响

| 项目 | 变化 |
| --- | --- |
| `Page` 大小 / 字段 | **不变**（仍 32 字节 / 20 字节） |
| `PageState` | **不变**（4 × `u16`，8 字节） |
| `BlockHeader` | **不变**（一个 cell，2 × `u16`） |
| `InitPage` / `BumpListCore` | 仅 feature 开启时 `BumpListCore` 多 `big_: UnsafeCell<BigPageList>`（2 个指针），第一页容量少 2 个 cell；feature 关闭时**不变** |
| 小页分配快路径 | **不变**（`fits_page_` 判断本来就有，超页时改走大页） |
| 小块释放快路径 | **不变**（`locate_block_` / `release_locked_` 均不加分支） |
| 页变空的分流 | 多一次 `is_large_()` 判断（冷路径）；小页清理函数本身不变 |
| `owner_ptr_` | 多与一个 bit 掩码（一条 AND 指令，feature 关闭时掩码值不变） |
| `free_non_root_pages_` | 小页循环不变，新增独立的大页循环（析构冷路径） |

`Page` 的 kind 没有占用 `PageState` 的字段，也没有扩大任何小块元数据；大页的额外
开销（`raw`、`size`、`align`）只出现在大页自己的 `BigPage` 头里。

## 4. 对外行为变化与待决事项

### 4.1 `AllocError` → 成功

当前 README、`lib.rs` 文档、`alloc_.rs` 单元测试与 `tests/allocator_.rs` 都明确写着
“未开启 `big_page` 时超过页容量返回 `AllocError`，不追加 Page”。开启 feature 后：

- 超页请求会成功（只要 backing 能提供）；
- `fixed_page_size_limits_allocation` / `oversized_request_is_rejected_without_page`
  等测试需要改成“分配成功、内容可读写、释放后 backing 计数配平”；
- `PageSize` 仍决定小对象的页粒度，但不再是单次分配的上限；
- `MAX_PAGE_BYTES` 仍表示单页上限，需要把文档里的“分配上限”改成“小页上限”。

这是**对外约定**的变化，按 `AGENTS.md` 第 1 条必须先确认。可选落地方式：

1. 直接默认启用，更新文档与测试（推荐，行为最自然）；
2. 加一个 `large_pages` 特性，默认开启或先默认关闭，给下游一个过渡期；
3. 新增构造选项（例如 `new_with_large_alloc(...)`），默认关闭——这会增加公开 API，
   需要单独讨论。

### 4.2 只按尺寸触发，还是也对齐失败回退

本文推荐 **v1 只按尺寸触发**：`fits_page_` 为假才走大页。这样：

- 现有“空 tail 因对齐放不下时返回 `AllocError`”的行为与测试保持不变；
- 超过页大小的请求一定成功（D1 的几何对任意对齐都成立）；
- 与用户提出的“超过页大小”目标完全一致。

如果团队希望 `Allocator` 对任意合法 `Layout` 都尽量成功，可以在小页路径失败后再尝试
大页。那会把 `empty_tail_alignment_failure_does_not_append` 的行为也改掉，并且可能为
一个 8 字节、1 MiB 对齐的请求付出 1 MiB 级开销，需要单独评估。建议作为后续可选项。

### 4.3 其他待决事项

- **大页上限**：默认不设额外上限，由 `Layout` 与 backing 决定；如需防止单次请求吃光
  内存，可以加一个可配置上限（公开 API，需讨论）。
- **大页缓存**：默认不缓存；后续可缓存“最后一个同布局空大页”。
- **错误可观测性**：大页申请失败仍返回 `AllocError`，不新增错误类型。
- **命名**：`BigPage` / `big_page_` / `BIG_PAGE_CELLS`；如有更贴合项目语境的
  命名可在实施前统一。

## 7. 风险与缓解

- **记账范围与数据范围分离容易被误解**：在 `BigPage`、`PageState` 初始化与
  `release_locked_` 附近写清不变量；用 debug 断言校验
  `base_ == h && cells_ == 1 && used_ <= 1`。
- **owner tag 的审计遗漏**：所有读取 `owner_` 的位置只允许通过
  `owner_ptr_` / `is_large_` / `try_lock_` / `PageGuard::drop`，并用
  `debug_assert_eq!(addr & PAGE_TAG_MASK, expected)`。
- **大页误入小页链表**：大页只走 `big_` 的 `link_after_` / `unlink_`；在
  `cleanup_empty_big_page_` 里用 debug 断言确认它确实在 `big_` 链表中。
- **析构顺序**：`free_non_root_pages_` 必须先取 `next` 再归还；大页与普通页分别用
  正确布局；`Core` 销毁前完成所有归还。
- **行为变化影响下游**：先获得同意，再统一更新 README、文档与测试；必要时用特性
  开关过渡。
- **对齐开销**：大页会浪费 `< align` 字节的前缀；这是保证用户指针对齐与“块头紧贴
  用户块”的代价，远小于额外开一个对齐页。

## 8. 小结

超页分配可以采用与小页**同构**的回收设计：

- 仍然用 `BlockHeader` 从用户指针 O(1) 找回 Page；
- 仍然用页锁保护块状态，用 `returned_ == used_` 判断整页已空；
- 仍然通过 `Page.owner_` 把“空页回收”升级给 `BumpListCore`，由它摘链并归还 backing。

区别只有三点：

1. 大页只放一个块，`PageState` 退化为 `base_ = h, cells_ = 1, used_ ∈ {0,1}`；
2. 大页自己的 backing 布局（`raw` / `size` / `align`）放在 `BigPage` 扩展头里，
   而不是固定在 `Core.page_size_`；
3. 大页挂在独立的 `BigPageList` 上、永不成为 `tail_`，释放后立即归还，不进入小页的
   空页缓存。

这样既不需要加宽任何小块元数据，也不需要全局注册表或第二套释放路径；小内存分配与
释放的热路径保持原样。实现结果见下一节。

  `cargo miri test --features big_page --test big_page_` 通过。

### 9.2 小页分配 / 回收性能

基准命令：

```bash
cargo bench --bench small_alloc
cargo bench --features big_page --bench small_alloc
```

工作负载：4 KiB 页，每批 64 个 32 字节小块，整批分配后全部归还（每批都会走一次
页变空的清理路径），取 5 轮最优值。本机同一进程外的重复运行结果（ns/op）：

| 配置 | 运行 1 | 运行 2 | 运行 3 |
| --- | ---: | ---: | ---: |
| `big_page` 关闭 | 72.56 | 72.70 | 72.30 |
| `big_page` 开启（小页循环） | 73.53 | 73.60 | 72.69 |
| `big_page` 开启（保持 64 KiB 大块存活） | 74.05 | 73.50 | 72.29 |

差异约 0.5% ~ 1.5%，与运行间抖动同一量级。结构上：

- feature 关闭时，`allocate_` 的超页分支仍直接返回 `Err`，`cleanup_empty_page_` 中
  没有 kind 判断，`BumpListCore` 不含 `big_` 字段；
- feature 开启时，小页分配成功路径与旧版相同；只有页变空时多一次 `is_large_()`，
  以及 `owner_ptr_` 多一个 bit 的掩码（一条 AND）；
- `free_non_root_pages_` 的大页循环只发生在 arena 析构。
